# Fly Fishing Counter Database

## Project URL
https://oqmdykrkbfdvvufgazsm.supabase.co

## Purpose

This database stores individual fish catches recorded by an ESP32
fish counter.

The ESP32 records catches while offline and uploads them in batches
when Wi-Fi becomes available. Each catch keeps its original timestamp,
even when uploaded later.

## Architecture

1. An administrator provisions each tracker with `public.provision_device(name)` and securely saves its returned `device_id`, `secret`, and `claim_code`.
2. The claim code is printed on the tracker. The secret is installed privately on the ESP32; it must not be printed or committed.
3. A user signs into the website through Supabase Auth and submits the sticker code to `public.claim_device(p_code)`.
4. `claim_device` binds the unclaimed device to `auth.uid()`; another account cannot claim that same device through the function.
5. The ESP32 records button presses, timestamps, and GPS coordinates locally, then sends authenticated HTTPS requests to `public.ingest_catch` when online.
6. The website reads the signed-in user's catches from `public.mycopy_fish_observations`, subject to RLS.

## Tables in use

- `public.users_data`: application user profiles keyed by `user_id` (linked to Supabase Auth).
- `public.devices`: registered tracker records and hashed credentials.
- `public.mycopy_fish_types`: fish species; IDs 1–4 were used in original prototype.
- `public.mycopy_fish_observations`: catch records, including `registered_device_id` and `user_id`.
- `public.device_settings`: per-device settings (exact current structure to be exported).
- `public.claim_attempts`: failed claim attempt log/rate limiting.

**Do not modify** the separate `public.fish_types` and `public.fish_observations` tables; they belong to a different subsystem.

### mycopy_fish_types

Stores the four trout categories:

| ID | Category |
|---|---|
| 1 | Brown Trout |
| 2 | Rainbow Trout |
| 3 | Brook Trout |
| 4 | Cutthroat Trout |

`color_of_fish` currently contains the category label rather than
a measured fish color.

### mycopy_fish_observations

Stores one row per fish caught.

| Column | Purpose |
|---|---|
| id | Database-generated UUID identifying the observation |
| fish_type_id | Foreign key referencing a fish category |
| caught_at | Original catch timestamp supplied by the device |
| latitude | Optional GPS latitude |
| longitude | Optional GPS longitude |
| location | PostGIS point generated from latitude and longitude |
| device_id | Unique identifier generated by the device |
| user_id | Unique identifier generated website when user account is created |
| registered_device_id | Unique id of ESP32 in use |

## Database Rules
- Each fish observation must reference a valid fish species in mycopy_fish_types.
- Each catch must include its original timestamp and GPS coordinates.
- Latitude must be between -90 and 90.
- Longitude must be between -180 and 180.
- PostGIS uses longitude first, latitude second.
- Each registered ESP32 has a unique device UUID.
- Each ESP32 is associated with a user through devices.user_id.
- Device registration uses a unique claim code generated during provisioning.
- Claim codes and private device secrets are stored as hashes in Supabase.
- A device can only be claimed if its user_id is currently NULL.
- Fish catches are automatically assigned to the registered device's owner.
- Unregistered devices are rejected by ingest_catch().
- Authenticated users can read only their own fish observations through RLS.

## Database Setup

The original SQL files were created for an earlier prototype and do not fully represent the current database.

The current Supabase database includes:

- `users_data` — user profiles associated with Supabase Authentication.
- `devices` — registered and unregistered ESP32 trackers.
- `device_settings` — device configuration data.
- `mycopy_fish_types` — supported fish species.
- `mycopy_fish_observations` — recorded fish catches.
- `claim_attempts` — registration attempt tracking.

The current database also uses three important PostgreSQL functions:

- `provision_device()` — generates a device UUID, private secret, and claim code.
- `claim_device()` — associates an unclaimed tracker with the currently authenticated website user.
- `ingest_catch()` — authenticates a device and inserts its catch under the registered owner's account.

## Device Provisioning and Registration

Each physical ESP32 must be provisioned before being distributed to a user.

During provisioning, Supabase generates:

1. A unique device UUID.
2. A private device secret used to authenticate uploads.
3. A unique claim code printed on the physical tracker.

The original private secret and claim code must be securely saved when generated. Supabase stores their hashes.

When a user receives their tracker:

1. They create an account or log in through the website.
2. They enter the claim code printed on their tracker.
3. The website calls `claim_device()` using the authenticated user's session.
4. Supabase matches the claim code to an unclaimed device.
5. The device's `user_id` is assigned to the logged-in user's UUID.

The same device cannot be claimed again through `claim_device()` once it has an owner.

## API Access and Security

Row Level Security (RLS) is enabled on:

- `users_data`
- `devices`
- `mycopy_fish_types`
- `mycopy_fish_observations`

Authenticated users can read their own registered devices and fish observations under the configured RLS policies.

Direct catch insertion through the public observations table API is not permitted for ordinary clients.

ESP32 devices upload catches through the `ingest_catch()` PostgreSQL function.

This function verifies the device UUID, private secret, active status, and registration status before inserting an observation.

The function assigns the observation's `user_id` using the registered device's owner, rather than trusting a user ID supplied by the ESP32.

**Example request body:**

```json

  "p_device_id": "YOUR_DEVICE_UUID",

  "p_fish_type": 1,
  "p_caught_at": "2026-10-25T23:30:40Z",
```

The private secret must never be committed to GitHub.

The ESP32 does not need the website user's access token for this upload process.

The `ingest_catch()` function assigns the correct user automatically.

**Current limitation:** The upload function does not yet accept a stable per-catch identifier. Duplicate protection for retries still needs to be implemented.

## Batch upload format

POST to:

```text
https://oqmdykrkbfdvvufgazsm.supabase.co/rest/v1/mycopy_fish_observations?on_conflict=device_record_id
```

Headers:

```text
apikey: YOUR_PUBLISHABLE_OR_ANON_KEY
Authorization: Bearer USER_ACCESS_TOKEN
Content-Type: application/json
Prefer: resolution=ignore-duplicates,return=representation
```

Example body:

```json
[
  {
    "fish_type_id": 1,
    "caught_at": "2026-10-10T16:00:00Z",
    "latitude": 40.015,
    "longitude": -105.2705,
    "device_record_id": "esp32-001-catch-000001"
  }
]
```

This is an example record ID. The firmware must guarantee uniqueness
across devices and restarts.

If GPS is unavailable, send null for both coordinates.

Do not supply `id` or `location`.

Existing device record IDs are ignored during retry uploads.
An invalid record can cause the entire batch to fail.

## ESP32 Firmware Requirements

- Detect and debounce all four species buttons.
- Map each button to the correct Supabase fish type ID.
- Record the original catch timestamp and GPS coordinates.
- Store catches in persistent memory when Wi-Fi is unavailable.
- Preserve stored catches through restarts and failed uploads.
- Send authenticated HTTPS requests to `rpc/ingest_catch`.
- Include the provisioned device UUID and private secret.
- Upload only after the device has been registered.
- Mark catches as uploaded only after confirmed success.
- Validate the server's HTTPS certificate.
- Support safe retries without creating duplicate observations.
