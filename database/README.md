# Fly Fishing Counter Database

## Purpose

This database stores individual fish catches recorded by an ESP32
fish counter.

The ESP32 records catches while offline and uploads them in batches
when Wi-Fi becomes available. Each catch keeps its original timestamp,
even when uploaded later.

## Architecture

- Device: ESP32 programmed using Arduino-style C++ in PlatformIO.
- Database: Supabase PostgreSQL.
- Geographic data: PostGIS.
- Communication: Supabase HTTPS REST API.
- Website: Static HTML and JavaScript using the REST API.

## Current prototype tables

The `mycopy_` prefix identifies the prototype tables.
I copied Orion's table with rename because I wasn't sure if I would mess it up in any way


### mycopy_fish_types

Stores the four trout categories:

| ID | Category |
|---|---|
| 1 | Brown Trout |
| 2 | Rainbow Trout |
| 3 | Brook Trout |
| 4 | Cutthroat Trout |

`color_of_fish` currently contains the category label rather than
a measured fish color.

### mycopy_fish_observations

Stores one row per fish caught.

| Column | Purpose |
|---|---|
| id | Database-generated UUID identifying the observation |
| fish_type_id | Foreign key referencing a fish category |
| caught_at | Original catch timestamp supplied by the device |
| uploaded_at | Timestamp when the database received the observation |
| latitude | Optional GPS latitude |
| longitude | Optional GPS longitude |
| device_record_id | Unique identifier generated by the device |
| location | PostGIS point generated from latitude and longitude |

## Database rules

- Each observation must reference an existing fish category.
- Catch timestamps are required.
- Device record IDs are required, nonblank, and globally unique.
- Latitude must be between -90 and 90.
- Longitude must be between -180 and 180.
- Both coordinates must be provided, or both must be null.
- The database generates `location`; clients do not upload it.
- PostGIS uses longitude first, latitude second.
- Retrying an upload must preserve the original device record ID.

## Setup for a fresh database

1. Run `001_schema.sql`.
2. Run `002_fish_types.sql`.
3. Create a prototype user under Supabase Authentication.
4. Replace `YOUR_TEST_USER_UID` in `003_permissions.sql`
   with that user's UID.
5. Run `003_permissions.sql`.

The schema script assumes PostGIS is installed in the `extensions`
schema. If PostGIS is already installed elsewhere, update the schema
references before running the script.

The setup scripts are initial migrations, not scripts that should
be rerun every time the device connects.

## Authentication and access

The prototype uses one dedicated Supabase Auth test account.

That account can:
- Read fish categories.
- Read prototype catches.
- Insert catches.

API updates and deletes are not granted.
Signed-out visitors have no access to these tables.

The device signs in using the test account and receives an access
token. Database requests include the project publishable/anon key
and the user's access token.

Passwords, access tokens, refresh tokens, and secret/service-role
keys must not be committed to GitHub.

## Batch upload format

POST to:

```text
https://YOUR_PROJECT_ID.supabase.co/rest/v1/mycopy_fish_observations?on_conflict=device_record_id
```

Headers:

```text
apikey: YOUR_PUBLISHABLE_OR_ANON_KEY
Authorization: Bearer USER_ACCESS_TOKEN
Content-Type: application/json
Prefer: resolution=ignore-duplicates,return=representation
```

Example body:

```json
[
  {
    "fish_type_id": 1,
    "caught_at": "2026-10-10T16:00:00Z",
    "latitude": 40.015,
    "longitude": -105.2705,
    "device_record_id": "esp32-001-catch-000001"
  }
]
```

This is an example record ID. The firmware must guarantee uniqueness
across devices and restarts.

If GPS is unavailable, send null for both coordinates.

Do not supply `id`, `uploaded_at`, or `location`.

Existing device record IDs are ignored during retry uploads.
An invalid record can cause the entire batch to fail.

## ESP32 implementation requirements

- Map each button to the correct fish category.
- Debounce buttons so one press records one fish.
- Store catches in persistent storage before uploading.
- Preserve original catch timestamps and record IDs through retries.
- Never reuse record IDs after restarting.
- Refresh expired authentication tokens.
- Retain queued records when uploads fail.
- Remove queued records only after confirming upload success.
- Validate HTTPS certificates.
